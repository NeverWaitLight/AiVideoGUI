# 文本模型调用层迁移计划

## 一、现状分析

### 1.1 当前架构问题

**双轨制实现，未统一使用 Provider 抽象：**
- `ChatService` 直接硬编码调用 DashScope API（`DASHSCOPE_TEXT_URL`）
- `../../providers` 目录下存在 `ChatProvider` 抽象基类和 `DashScopeChatProvider` 实现
- 但 `ChatService` 并未使用这些 Provider 类，而是直接调用 requests

**代码重复和维护成本高：**
- `ChatService` 的每个业务方法（`chat()`, `generate_script()`, `generate_storyboard()` 等）都重复实现了：
  - HTTP 请求逻辑
  - 重试机制
  - 错误处理
  - 任务状态追踪
  - 响应解析
- 如需支持新的文本模型提供商，需要大量修改 `ChatService` 代码

**配置未生效：**
- `settings.json` 中定义了 `chat_providers` 列表（DeepSeek、OpenAI、Anthropic 等）
- 但实际运行时只使用 DashScope，其他配置项未生效
- `ConfigManager` 已支持多 Provider 配置，但未被充分利用

### 1.2 现有代码结构

```
providers/
  ├── chat_base.py          # ChatProvider 抽象基类（已存在，但未使用）
  ├── dashscope_chat.py     # DashScope 实现（已存在，但未使用）
  └── ...

service/
  └── chat_service.py       # 直接硬编码 DashScope API 调用（785 行）

config/
  └── manager.py            # ConfigManager 支持多 Provider 配置
```

**调用链路：**
```
Bridge → ChatService.optimize_story_outline()
           ↓ 构建 messages
         ChatPromptBuilder.build_outline_optimization_messages()
           ↓ 直接调用 DashScope API（硬编码）
         requests.post(DASHSCOPE_TEXT_URL, ...)
           ↓ 返回文本
         解析响应 → 更新任务状态 → 返回结果
```

## 二、目标架构

### 2.1 核心目标

**统一文本模型调用接口：**
- 使用 `any-llm-sdk` 库替代直接的 HTTP 调用
- 一个实现类支持绝大部分文本大模型（OpenAI、Anthropic、DeepSeek、DashScope 等）
- 符合 OpenAI Chat Completions API 标准

**保持配置方案不变：**
- `settings.json` 中的 `chat_providers` 配置结构保持不变
- 在新的 Provider 类中做兼容处理，映射配置到 `any-llm-sdk` 的参数

**简化 ChatService 代码：**
- `ChatService` 通过 Provider 抽象调用文本模型
- 移除重复的 HTTP 请求、重试、错误处理逻辑
- 保留任务追踪、日志记录、业务编排逻辑

### 2.2 新架构设计

```
providers/
  ├── chat_base.py                    # ChatProvider 抽象基类（保留）
  ├── unified_chat_provider.py        # 新增：基于 any-llm-sdk 的统一实现
  ├── dashscope_chat.py               # 废弃（可选保留作为兼容）
  └── ...

service/
  └── chat_service.py                 # 重构：通过 Provider 调用，移除硬编码

config/
  └── manager.py                      # 保持不变
```

**新调用链路：**
```
Bridge → ChatService.optimize_story_outline()
           ↓ 构建 messages
         ChatPromptBuilder.build_outline_optimization_messages()
           ↓ 调用 Provider 抽象
         UnifiedChatProvider.chat(messages)
           ↓ 使用 any-llm-sdk
         any-llm-sdk 自动适配各厂商协议
           ↓ 返回文本
         ChatService 解析响应 → 更新任务状态 → 返回结果
```

## 三、技术方案

### 3.1 any-llm-sdk 简介

`any-llm-sdk` 是一个统一的 Python LLM 调用库，支持以下特性：
- **统一接口**：符合 OpenAI Chat Completions API 标准
- **多厂商支持**：自动适配 OpenAI、Anthropic、DeepSeek、DashScope、Gemini 等
- **配置驱动**：通过 `base_url` 和 `api_key` 切换提供商
- **内置重试**：支持超时重试和错误处理
- **流式响应**：支持 SSE 流式输出（可选）

### 3.2 配置映射方案

**当前配置格式（`settings.json`）：**
```json
{
  "providers": [
    {
      "provider_name": "dashscope",
      "api_key": "sk-xxx",
      "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
      "default_model": "qwen-max",
      "default_params": {}
    },
    {
      "provider_name": "deepseek",
      "api_key": "sk-xxx",
      "base_url": "https://api.deepseek.com/v1",
      "default_model": "deepseek-chat",
      "default_params": {}
    }
  ],
  "app_settings": {
    "default_chat_provider": "dashscope"
  }
}
```

**映射到 any-llm-sdk 参数：**
```python
# UnifiedChatProvider 内部转换
client = ChatClient(
    api_key=config.api_key,
    base_url=config.base_url,  # any-llm-sdk 通过 base_url 识别厂商
    timeout=1800,
)

response = client.chat.completions.create(
    model=config.default_model,
    messages=messages,
    **config.default_params,  # 透传用户自定义参数
)
```

### 3.3 兼容性处理

**DashScope 特殊参数适配：**
- 当前 `ChatService.generate_script()` 使用 `max_tokens=16384`
- 需在 `default_params` 中配置或在 Provider 内部自动补充

**错误信息映射：**
- `any-llm-sdk` 抛出的异常需要映射为用户友好的错误消息
- 保留现有的任务状态更新逻辑（`succeeded`/`failed`）

**响应格式统一：**
- `any-llm-sdk` 返回标准 OpenAI 格式：`response.choices[0].message.content`
- 与当前 DashScope 响应格式一致，无需额外转换

## 五、关键代码示例

### 5.1 UnifiedChatProvider 实现

```python
# providers/unified_chat_provider.py
from loguru import logger
from any_llm_sdk import ChatClient
from models.provider_config import ProviderConfig
from providers.chat_base import ChatProvider

class UnifiedChatProvider(ChatProvider):
    """基于 any-llm-sdk 的统一文本模型调用实现"""

    def __init__(self, config: ProviderConfig) -> None:
        super().__init__(config)
        self._client = ChatClient(
            api_key=config.api_key,
            base_url=config.base_url,
            timeout=1800,
        )

    def chat(
        self, 
        messages: list[dict[str, str]], 
        model: str | None = None,
        **kwargs
    ) -> str:
        """调用文本模型生成内容"""
        model = model or self._config.default_model
        params = {**self._config.default_params, **kwargs}
        
        logger.info(f"调用文本模型：provider={self.provider_name}, model={model}")
        
        try:
            response = self._client.chat.completions.create(
                model=model,
                messages=messages,
                **params
            )
            content = response.choices[0].message.content.strip()
            logger.info(f"文本生成成功：长度={len(content)} 字符")
            return content
        except Exception as e:
            logger.exception(f"文本模型调用失败：{e}")
            raise RuntimeError(f"文本模型调用失败：{e}")

    def list_available_models(self) -> list[str]:
        """获取可用模型列表"""
        try:
            response = self._client.models.list()
            return [model.id for model in response.data]
        except Exception as e:
            logger.warning(f"获取模型列表失败：{e}")
            return []
```

### 5.2 重构后的 ChatService.chat()

```python
# service/chat_service.py (重构后)
def chat(
    self,
    messages: list[dict],
    model: str | None = None,
    project_id: int | None = None,
    project_name: str | None = None,
    module: str = "storyboard",
    context: str | None = None,
    caller_type: GenerateTaskCallerType | None = None,
    caller_id: str = "",
    parent_ids: str = "",
) -> tuple[str, int]:
    provider_config = self._config.get_provider_config(
        name=self._config.settings.default_chat_provider,
        provider_type="chat"
    )
    if not provider_config or not provider_config.api_key:
        raise RuntimeError("未配置文本模型 API Key，请在设置中配置")

    model = model or provider_config.default_model

    # 创建 generate_task 记录
    provider_task_id = str(uuid.uuid4())
    request_params = json.dumps({
        "messages": messages,
        "model": model,
        "module": module,
        "context": context,
        "project_id": project_id,
        "project_name": project_name,
    }, ensure_ascii=False)

    task_repo = self._sm.get_repo(repo_class=GenerateTaskRepository)
    self._sm.begin_write()
    try:
        task_id = task_repo.add(
            provider_task_id=provider_task_id,
            provider_name=provider_config.provider_name,
            model_name=model,
            local_path="",
            request_params=request_params,
            type=GenerateTaskType.CHAT,
            caller_type=caller_type,
            caller_id=caller_id,
            project_id=project_id,
            parent_ids=parent_ids,
        )
        self._sm.commit_write()
    except Exception:
        self._sm.rollback_write()
        raise

    logger.info(f"文本对话任务已创建：task_id={task_id}, model={model}")

    # 调用 Provider（移除所有 HTTP 请求代码）
    try:
        content = self._provider.chat(messages=messages, model=model)
        
        # 更新任务状态为成功
        self._sm.begin_write()
        try:
            task_repo.update_status(task_id, "succeeded")
            task_repo.mark_completed(task_id)
            self._sm.commit_write()
        except Exception:
            self._sm.rollback_write()

        return content, task_id

    except Exception as e:
        # 更新任务状态为失败
        self._sm.begin_write()
        try:
            task_repo.update_status(task_id, "failed", error_message=str(e))
            task_repo.mark_completed(task_id)
            self._sm.commit_write()
        except Exception:
            self._sm.rollback_write()
        raise
```

## 六、风险与应对

### 6.1 潜在风险

| 风险项 | 影响 | 应对措施 |
|--------|------|---------|
| `any-llm-sdk` 与某些提供商不兼容 | 部分模型无法调用 | 保留 `ChatProvider` 抽象，允许特殊提供商自定义实现 |
| 响应格式差异导致解析失败 | 业务功能异常 | 在 Provider 层统一响应格式，确保返回标准结构 |
| 重试机制变更导致超时问题 | 用户体验下降 | 测试环节重点验证长时间任务的稳定性 |
| 配置迁移遗漏导致旧配置不可用 | 用户无法使用 | 编写配置迁移脚本，自动检测并升级旧配置 |
| 依赖库版本冲突 | 安装失败 | 使用 `uv` 管理依赖，确保版本兼容性 |

### 6.2 回滚方案

如果迁移后出现严重问题，可以快速回滚：
1. 恢复 `ChatService` 的旧实现（保留 Git 历史）
2. 临时禁用 `UnifiedChatProvider`，使用旧的硬编码调用
3. 修复问题后再次尝试迁移
